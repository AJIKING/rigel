## 1. 目的（なぜ）

特訓の4種目めとして、**清一色手で「どれを切ると一番広いか」を即断する**訓練を足す。
既存「清一色 何待ち」は待ちを当てる（読み）、既存「牌効率」は混色の受け入れ（基礎）。
本種目は**全打牌パターンを同時に評価する**必要があり、特訓の最上位難度を埋める。

## 2. ハーネス構成要素

**ツール（決定的アルゴリズム）** と **検証**。AI は非関与で、出題も採点も `@rigel/ui` の
純関数が持つ（既存3種目と同じ規律）。採点ロジックを画面に二重実装しない。

## 3. スコープ

**やること**

- `QuizKind` に1種目追加（`"chinitsuUkeire"`）。単色14枚 → 1枚切る
- 正解 = **最小向聴を保つ打牌**のうち、切った後に**向聴が1つ進む同色牌**が最も多いもの（同率は全部正解）
  - テンパイ手 → 待ち枚数最大 ／ 1向聴手 → 受け入れ枚数最大
- 出題は**テンパイ / 1向聴を1問ごとに 1/2 でランダム**。テンパイ問題は**打牌候補4種以上**を下限にする
- `discardUkeires` に受け入れ候補を絞る口を足し、見直しの受け入れ詳細も同色限定に揃える
- web / mobile の特訓画面・`/dev/training` への配線、文言、マイページの種目フィルタ

**やらないこと（非対象）**

- **2向聴の出題** — 単色14枚に2向聴は存在しない（§4 で実測確定）
- 手牌に他色・字牌を混ぜること（「清一色に向かう途中の手」は別種目の話）
- **2段目指標**（受け入れ同数を「テンパイ時の待ちの広さ」で割る）— 将来の難易度オプション
- 場況（河・副露）による残り枚数の控除 — 既存 `ukeire.ts` の v1 方針を踏襲
- 問題の DB 保存・サーバ採点 — 既存どおりクライアント生成・クライアント採点
- 設計ドキュメント 2章の非スコープ（点数の自動計算はしない／AI 非関与／画像を扱わない）はそのまま適用

## 4. `[決定]` / `[未確定]` の仕分け

**依拠する `[決定]`**

- 特訓クイズ（60秒タイムアタック・無料1日3回・出題は決定的アルゴリズム・成績は本人のみ）
  （※ここに挙げた前提のうち 無料枠/匿名/成績公開範囲/採点の確定 は 2026-08-04 に転換済み。
  [quiz-open-and-ranking.md](quiz-open-and-ranking.md) 参照。本種目の出題仕様には影響なし）
- 受け入れの定義（`ukeire.ts` v1: 残り枚数 = 4 − 自分の手牌内使用枚数。場況は見ない）
- 「同率は全部正解」「向聴戻しは正解にしない」（既存 `bestUkeires`）

**本 Plan で新たに `[決定]` にすること（検証は着手前に完了済み）**

| 項目 | 検証結果 |
|---|---|
| 清一色14枚に2向聴は存在するか | **存在しない**。全118,800通り（各牌0〜4枚・合計14枚）を総当たり: −1向聴 11.18% / 0向聴 77.04% / 1向聴 11.78% / **2向聴 0通り** |
| 生成が60秒セッションに耐えるか | テンパイ（候補4種以上）**6.3ms** / 1向聴 **31.7ms**（既存「牌効率」12.1ms） |
| 出題の質 | テンパイ: 打牌候補5.05種・正解一意75%・1位2位差2.38枚 ／ 1向聴: 候補7.60種・正解一意60%・**差1.47枚** |
| 「聴牌優先」を別ルールで書く必要があるか | **不要**。1向聴14枚から切ってテンパイになる打牌は 0/200手 → 「最小向聴を保つ」1ルールで両方を表現できる |
| 他色が受け入れに混ざるか | 混ざる（1向聴手の約5%が七対子経由）→ **同色9種に限定して数える**必要あり |

**触れる `[未確定]`**: なし。

## 6. 信頼まわり

- **Zod 検証**: AI 非関与のため AI 出力の parse は**該当なし**。サーバ側は既存 `QuizResultSchema`
  がそのまま効く（新種目でも `kind` が enum で弾かれる）
- **推測しない（null 白旗）**: 該当なし（写真解析を通らない。手牌は生成器が作る確定牌）
- **課金カウント**: 新規のカウントは**足さない**。既存の「無料1日3回・セッション開始時に消費」
  に相乗りする（`FREE_QUIZ_PER_DAY`）。種目を増やしても1日の枠は増えない
- **画像非保存**: 該当なし（画像を扱わない）
- **プライバシー**: 成績は本人のみ（`GET /quiz/sessions` は認証必須・本人の行のみ）。
  問題・回答はサーバに送らない
- **既知の前提（変更なし）**: 採点はクライアント側で、サーバは `total/correct` を検証できない

## 9. 検証 / eval 方針

- **ゲート**: `pnpm typecheck / lint / format:check / test / build`（開発ガイド04）
- **eval**: AI 非関与のため精度 eval は不要。代わりに**総当たり検証**を1つテストに残す —
  「単色14枚に2向聴は存在しない」は仕様の土台なので、縮小版（サンプリング）で回帰テスト化する
  （フル118,800通りは約99秒かかるため CI には載せない）
- **性能の目安**はテストに焼かない（マシン依存で不安定）。リスクとして監視する

## 10. リスク / 未決事項

- **生成コスト 31.7ms/問（1向聴）**。原因は `shanten()` が単色手で重いこと（単色13枚 0.29ms・
  14枚 0.65ms）。60秒で20問なら合計0.4秒程度で許容だが、体感が悪ければ単色専用の高速化
  （9種 counts をキーにしたメモ化 or 単色シャンテン表）を別 Plan で検討する
- **1向聴は正解一意率60%**（同率が4割）。「同率は全部正解」で吸収するが、正答率が高めに
  出る可能性がある。運用後に難易度を見て、2段目指標の導入を再検討
- **`QUIZ_CARD_MOTIF` の絵柄**が既存3種目と衝突しないか（清一色=索子、牌効率=筒子を使用済み）。
  萬子で差別化する
- 単色14枚を一様抽選するため、**実戦の清一色手とは形の分布が違う**（既存「清一色 何待ち」と
  同じ性質）。運用後に必要なら生成方法を見直す
