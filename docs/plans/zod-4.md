# Plan: zod 3 → 4 移行（スキーマ背骨のメジャー更新）

> 状態: **起案（未着手）**。単独では価値が薄いため、スキーマに大きめの変更が入るタイミング
> （または zod 3 のメンテ終了アナウンス）に合わせて着手する。
> 関連: [07 依存固定台帳](../開発ガイド/07_依存固定台帳.md)

## 1. 目的（なぜ）

牌譜スキーマ（全層共有の背骨）を維持しつつ zod を現行メジャーに揃え、
エラー表現の改善・パフォーマンス向上・将来の依存解決の詰まり（zod 3 前提のライブラリ減少）を回避する。

## 2. ハーネス構成要素

ツール（スキーマ）。**AI 出力の検証（`*.parse()`）そのもの**に触れるため信頼ゲートの中核。

## 3. スコープ

- やること:
  - @rigel/schema / api の zod を 4 系へ更新し、破壊的変更（error API・`.default()` 挙動・
    `z.record` 系のシグネチャ・`superRefine`/issue 形式など）へ追随
  - api のエラーレスポンス整形（ZodError を使う箇所）の互換確認
- やらないこと:
  - スキーマの意味的変更（フィールド追加・制約変更はしない。挙動は現状維持）

## 4. `[決定]` / `[未確定]` の仕分け

- 依拠する `[決定]`: スキーマが背骨・AI 出力は使う前に必ず parse（CLAUDE.md ハードルール3）
- `[未確定]`: なし（純粋な依存更新）

## 5. 影響範囲

- packages/schema（本丸）・apps/api（parse/エラー整形）・packages/ui / client / web / mobile（型の波及）
- スキーマ（背骨）への影響: **全部**。だからこそテストが移行の安全網になる

## 6. 信頼まわり

- Zod 検証: 既存の parse 位置は変えない。**既存テスト（null スロット・スキーマ違反・境界）が
  すべて緑のまま**であることが移行の完了条件
- 推測しない / 課金 / 画像非保存: 挙動変更なし（変更が出たら移行のバグ）

## 7. 受け入れ条件

- [ ] 全ワークスペースの typecheck / test が緑（schema のテストは無修正で通るのが理想。
      エラーメッセージ形式に依存するテストだけ期待値更新を許容）
- [ ] AI 出力の不正データが従来どおり 4xx/検証エラーで弾かれる（api の異常系テスト緑）

## 8. Task 分解

1. [ ] zod 4 の破壊的変更を洗い出し、schema 内の該当 API を列挙（コード調査）
2. [ ] @rigel/schema を更新 → Red になったテストを1件ずつ Green に
3. [ ] api のエラー整形・異常系を追随
4. [ ] ui / client / web / mobile の型波及を解消 → 全ゲート緑

## 9. 検証 / eval 方針

ゲート＝ルート `pnpm typecheck / lint / test / build`。AI 精度には無関係（eval 不要）だが、
検証エラーの HTTP 挙動が変わっていないことを api の異常系テストで確認する。

## 10. リスク / 未決事項

- ZodError の issue 形式変更が api のエラーレスポンス（クライアント表示）に漏れる
- zod 4 の `z.infer` 挙動差で共有型が微妙に変わり、ui/client の型が広く赤くなる可能性

## 11. 完了の定義

- [ ] 受け入れ条件が全て緑
- [ ] 台帳の凍結枠「zod 3.25」を削除
