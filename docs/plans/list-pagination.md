# Plan: 一覧のページネーション（カーソル方式）と全件走査の解消

> 承認: 2026-08-04（オーナー指示「設計を Plan に起こしてから着手」）。細部の既定値は本文に明記。
> 関連: [タスク分解とPlan運用](../開発ガイド/03_タスク分解とPlan運用.md) / [05 APIアーキテクチャ](../開発ガイド/05_APIアーキテクチャ.md)
> 前提（2026-08-04 調査）: リポジトリ全体でページネーション・無限スクロール・カーソル/オフセットは
> 未実装。公開牌譜=60件切り捨て（内部は直近公開局200行の窓）・公開何切る=50件切り捨て・
> マイページ各種と公開ユーザーページは **LIMIT なしの全件返却**（公開ユーザーページは匿名で誘発可）。

## 1. 目的

1. **切り捨ての解消**: 公開牌譜・公開何切るで、上限を超えた過去データに到達できるようにする
   （公開牌譜は「直近200公開局の窓」という構造穴も同時に潰す）
2. **全件走査の解消**: マイページ各種・公開ユーザーページの LIMIT なしクエリを止め、
   データ量に比例して遅くなる経路を塞ぐ（公開ユーザーページは負荷対策も兼ねる）
3. web/mobile とも「続きを読む」体験を統一の形で提供する

## 2. ハーネス構成要素

- スキーマ: カーソルの encode/decode と検証を背骨（@rigel/schema）に一元化（不正カーソルは 400）
- 制約: ページサイズは**サーバ固定**（クエリで受けない＝1リクエストの読み取り量に上限を保証）
- AI 非関与

## 3. 設計（[決定] 2026-08-04 実装既定）

### 3-1. カーソル方式（offset は不採用）

- **形**: 不透明文字列 `"<epochMs>_<id>"`。背骨に `encodeListCursor / decodeListCursor`（Zod 検証つき。
  ms=正の整数・id=1〜80文字）。デコード失敗は usecase が `invalid`（400）。
- **並び**: 基準時刻 DESC・同時刻は id DESC のタイブレーク（安定・重複/欠落なし）。
- **取得**: `LIMIT pageSize+1` で読み、余った1件の有無で `nextCursor` を決める
  （`WHERE (t < :ms) OR (t = :ms AND id < :id)`。集約クエリは HAVING で同条件）。
- offset を使わない理由: D1（SQLite）で深い OFFSET は走査コスト線形・行の挿入で重複/欠落が起きる。

### 3-2. レスポンス形（wire）

- 一覧 API は `{ items: T[], nextCursor: string | null }` に統一（@rigel/client の `Page<T>`）。
- **既存の「配列を直接返す」形からの breaking change**。許容根拠: mobile は未リリース
  （ストア登録前）・web は API と同時デプロイ。**ストアリリース後にこの種の変更をする場合は
  互換レイヤ（旧形の並行提供）が必須**である旨をここに残す。

### 3-3. ページサイズ（サーバ固定・実装既定値）

| 一覧 | サイズ | 備考 |
|---|---|---|
| 公開牌譜 GET /games/public | 30半荘 | 従来60を2ページに分割相当 |
| 公開何切る GET /problems | 30問 | |
| 公開ユーザーページ /users/:idOrHandle/profile | 20半荘 | profile 本体＋初回ページ同梱。以降 `?cursor` |
| マイページ牌譜 GET /me/games | 30半荘 | |

| お気に入り GET /favorites | 30件 | |

### 3-4. 各一覧のカーソル基準

| 一覧 | 基準時刻 | タイブレーク id | クエリの芯 |
|---|---|---|---|
| 公開牌譜 | **その半荘の最新公開局** の createdAt | gameId | `game_logs WHERE visibility='public' AND status='complete' GROUP BY game_id` を `MAX(created_at)` で並べ、HAVING でカーソル適用。**「直近200公開局の窓」を廃止**し公開半荘を直接ページング（切り捨て構造穴の根治） |
| 公開何切る | problems.createdAt | id | 既存 `problems_status_idx(status, createdAt)` が効く |
| 公開ユーザーページ | 同・最新公開局 createdAt | gameId | 公開牌譜と同じ集約クエリに `userId` 条件を足す（全半荘×全局の走査を廃止） |
| マイページ牌譜 | games.createdAt | gameId | `games_user_idx` |
| マイ何切る | problems.createdAt | id | `problems_user_idx` |
| お気に入り | favorites.createdAt | `targetType:targetId` | 複合キーなので id 部は連結文字列 |
| 解析下書き | createdAt | id | |

### 3-5. クライアント UI（実装既定値）

- **web**: 一覧末尾に**「もっと見る」ボタン**（明示的・SSR初期ページ＋クリックで追記。
  無限スクロールは将来オプション）。読み込み中はボタンを busy 表示。
- **mobile**: FlatList の **onEndReached で無限読み込み**＋フッタスピナー
  （モバイルの標準体験。多重発火は取得中フラグでガード）。
- 取得失敗時は既存の流儀（LIST_LOAD_ERROR_MESSAGE＝「0件」と混同させない）で行末に表示し再試行可。
- **絞り込み（filterPublicFeed 等）は「読み込み済みの範囲」に対して働く**（既定。全件検索は
  別機能=サーバ検索の話なので本 Plan では扱わない）。

### 3-6. 対象外（現状維持とその理由）

- **ランキング**: 上位50＋自分の順位で完結（[決定] 2026-08-04）。集計のマテリアライズは規模が
  出てから（quiz-open-and-ranking.md 記載どおり）
- **特訓履歴 GET /quiz/sessions**: LIMIT 500＋`?since` が既にあり、UI は直近20件＋期間グラフで
  消費。500件=約8ヶ月毎日10回分で当面十分。超えたら `since` の活用から着手
- **半荘内の局一覧**（1半荘30局上限）・見直しレコード（100問上限）: 上限が小さく固定

### 3-7. 初回ページの供給と sitemap

- web の公開一覧（/kifu, /problems）は**サーバコンポーネントが1ページ目を取得**して渡し、
  「もっと見る」以降はサーバアクション経由（既存の流儀）。
- sitemap は公開牌譜をページ辿りで最大 **200半荘**（実装既定値）まで列挙（現状の60件上限を拡大。
  それ以上は個別ページの被リンクに任せる）。

## 4. リスク

- **breaking change**: 3-2 のとおり未リリース前提で許容。デプロイは api → web の順（web 旧版が
  新 API を読んでも `items` 参照で落ちるのは配列形前提のコードのみ＝同時デプロイで実質無風）。
- **並び順の変化**: 公開牌譜は「窓の中の並び」から「最新公開局時刻の全体順」になる（正しい方に寄る）。
- **絞り込みの見え方**: フィルタ結果が「読み込んだ範囲」に限られる（3-5 既定。件数が伸びたら
  サーバ側フィルタを別 Plan で）。
- **お気に入りの整合**: ページ跨ぎで対象削除があると件数が欠けて見える（従来と同じ・許容）。
- **favorites/mygames の N+1**: ページサイズで有界化される（30件×付随クエリ）。完全解消
  （JOIN 化）は本 Plan の対象外・別途。

## 7. 実装ノート（2026-08-04 完了時の逸脱・補足）

- **解析下書き（GET /problems/drafts）は 3-3 の逸脱＝ページ化しない**: 下書きは正規保存/破棄で
  畳まれる一時データで、件数は解析枠（下書きは解析実行ごとに先行作成）で自然に有界。一覧は
  ポーリング（5秒）で丸ごと再取得する画面のため、ページ UI は過剰と判断。**LIMIT も付けない**
  （一度 LIMIT 100 を入れたが、退会時の R2 写真掃除（DeleteAccount）が `listByUser` の全件列挙に
  依存しており、欠けるとルール7「データ削除で必ず消す」に穴が開くため品質パスで撤回）。
- **GET /games（半荘の素の一覧）は廃止**: ページ化してみたものの消費者ゼロ（web/mobile とも
  件数つきの GET /me/games を使う）と判明したため、ルート・usecase・client ごと削除した。
- **お気に入りのページは「付けた順」の混在1本**: サーバーが1ページ（30件）を引いてから
  半荘/何切るへ振り分けて `{games, problems, nextCursor}` で返す。ページ内の種別内訳は
  不定（片方 0 件のページもあり得る）。クライアントは両配列を追記するだけ。
- **マイページの refetch（解析完了・フォーカス・ポーリング）は先頭ページへ戻す**:
  追加読み込み済みの範囲は畳まれる。最新状態の反映を単純さ優先で採った（重複・欠落を
  避ける再ウォークはしない）。取得中カーソルの固定で refetch と loadMore の競合による
  stale 追記を防ぐ。
- **共通化（品質パス 2026-08-04）**: decode＋`+1`＋切り分けは api の `fetchPage`
  （application/pagination.ts）、クライアントの追加読み込みは web `lib/use-load-more.ts`＋
  `LoadMoreButton` / mobile `lib/use-load-more.ts`＋`ListFooter` に一本化。個別実装の発散が
  生んだ2バグ（refetch 競合で「もっと見る」が固まる／プロフィール遷移で前の人の半荘が混ざる）
  もこの一本化で解消。keyset 用の複合 index（games/problems の `(userId, createdAt)`）は
  migration 0020。
- **既知の制約（対応は必要になったら別 Plan）**:
  - お気に入りタブの統計3枠・牌譜タブの保存枠（非公開/下書き x/5）は「読み込み済みの範囲」の
    件数（31件以上あると過少表示。正確にするならサーバ集計が要る。refactor バックログに記載）。
  - mobile はフィルタ・検索で表示が0件になると FlatList ごと消えるため onEndReached の口が無く、
    続きが読み込み済み範囲の外にあっても手動で辿れない（web は「もっと見る」が残るので可能）。
    空状態への読み込み導線は必要になったら追加。
