# Plan: 撮影画像の恒久保存（元写真を牌譜に残す）

> 状態: **提案（未承認・2026-08-02）**
> 背景: オーナー発案「ログとして残すのが良い。ユーザーにとっても残すのは価値がある」
> （2026-08-02）。**ハードルール7「画像を恒久保存しない」（[決定]）の変更**を伴うため、
> 本 Plan の承認をもって [決定] を更新してから実装に入る。
> 関連: [async-analysis.md](async-analysis.md)（R2 一時保存・ジョブ基盤を土台に使う）

## 1. 目的（なぜ）

解析に使った撮影写真を牌譜（半荘・局）に紐づけて残し、あとから見返せるようにする。

- **検証**: AI の読み取りを元写真と突き合わせて確認・修正できる（目検必須のドラフトという
  信頼原則を UI で支える）
- **記録**: 「あの日の卓」が写真ごと残る。牌譜データだけより思い出・共有価値が高い
- **再解析**: 恒久保存があれば「もう一度解析」の 1日期限（retry_expired）も将来なくせる

## 2. ハーネス構成要素

**記憶・状態**（写真の恒久ストア + メタの D1）＋**権限**（所有者のみ配信）＋**制約**（削除連鎖）。
AI パイプライン自体は不変（前処理・スキーマ・検証に変更なし）。

## 3. スコープ

- やること:
  - 牌譜解析（/analyze）が **done になったとき**、一時画像を恒久バケットへ移して局に紐づける
    （河＝常時。手牌写真・1枚モードもそのまま）
  - 写真メタの D1 テーブル `photos`（id / userId / gameId / logId / kind / r2Key / size / createdAt）
  - 配信 API（**所有者のみ**。公開半荘でも写真は所有者だけが見られる＝安全側の既定）
  - web / mobile の閲覧 UI（半荘詳細・盤面に「元写真」導線）
  - 削除連鎖: 局削除・半荘削除・退会で写真（R2 + D1 行）も確実に消す
  - プライバシーポリシー改稿（「保存する・所有者のみ閲覧・削除で消える」を明記）
- やらないこと（v1 非対象）:
  - 何切る（/problems/analyze）の写真保存（ドラフトは保存されないため紐づけ先が無い）
  - 写真の公開・共有（公開半荘への写真掲載オプションは将来判断）
  - 画像の圧縮・リサイズ（v1 は原本保存。Photon による再エンコードは将来最適化）
  - 過去に解析済みの半荘への遡及（一時画像は消えているため不可能）

## 4. `[決定]` / `[未確定]` の仕分け

- **変更する [決定]**（本 Plan 承認時に CLAUDE.md ルール7・AGENTS.md・設計ドキュメントを更新）:
  - 旧: 画像を恒久保存しない（R2 一時保存のみ・処理後削除）
  - 新: **牌譜解析に使った撮影画像は、解析成功時に恒久保存して局に紐づける**。
    閲覧は所有者のみ。局・半荘・アカウントの削除で必ず消す。
    一時バケット（rigel-analysis-tmp・TTL 1日）の役割は「ジョブ搬送＋失敗リトライ」のまま
- 新規 [未確定]（v1 では安全側に倒し、実運用を見て判断）:
  - 保存容量の上限（v1 は上限なし。使用量は解析枠 = 月100/320回 × 数枚 × 数MB で有界に増える。
    ストレージコストが問題になったら圧縮 or プラン別上限を導入）
  - 公開半荘での写真公開オプション（v1 なし）
  - 「もう一度解析」の恒久写真化（retry_expired の撤廃。v1 は現行の1日期限のまま）

## 5. 影響範囲

- インフラ: **新規 R2 バケット `rigel-photos`**（TTL なし。tmp はバケット全体に1日ルールが
  掛かっているため分離が必須）＋ wrangler.toml バインディング `PHOTOS`
- apps/api:
  - migration: `photos` テーブル（users への FK。退会カスケードに追加＝消し漏らすと退会が
    FK 違反で落ちる）
  - domain/infra: `PhotoRepository`（D1）+ `PhotoStore`（R2 恒久）
  - RunAnalysisJob: done 時 `deletePrefix` → **恒久バケットへ move + photos 行作成** に変更
    （失敗時は従来どおり tmp に残す）
  - routes: `GET /games/:id/photos`（メタ一覧）/ `GET /photos/:id`（バイト配信・所有者のみ・404で存在を漏らさない）
  - 削除連鎖: DeleteKifu / DeleteGame / DeleteAccount（analysis_jobs の掃除と同型）
- packages/client: `listGamePhotos` / 写真取得
- apps/web / mobile: 半荘詳細に「元写真」ビュー（v1 は一覧＋拡大表示のみ）
- スキーマ（背骨）への影響: **なし**（Kifu は不変。写真メタは API 層）
- 依存追加: なし

## 6. 信頼まわり

- **プライバシー**: 写真は所有者のみ閲覧（公開半荘でも露出しない）。API は他人・未ログインに
  404（存在も漏らさない）。email 同様、レスポンスに R2 の生キーを含めない（photoId で引く）
- **削除の責務**: 局・半荘・退会の3経路すべてで R2 + D1 を掃除（テストで固定）。
  ポリシー明記「削除すると写真も消える」
- **課金**: 変更なし（写真保存は解析成功の副産物。追加課金なし）
- **画像の出所**: 保存するのは自分がアップロードした原本のみ（AI 生成物や他人の画像は入らない）

## 7. 受け入れ条件（= 最初に書く失敗テストの集合）

- [ ] 解析 done で一時画像が恒久バケットへ移り、photos 行（logId 紐付き）ができる。tmp は空
- [ ] 解析 failed では恒久保存しない（従来どおり tmp 残し・リトライ可）
- [ ] GET /games/:id/photos は所有者に一覧、他人・未ログインに 404
- [ ] GET /photos/:id は所有者にバイト（contentType 付き）、他人に 404
- [ ] 局削除でその局の写真が消える／半荘削除で配下全写真が消える／退会で全写真が消える
      （FK 違反で退会が落ちないこと）
- [ ] web / mobile: 半荘詳細から元写真を開ける（写真が無い半荘には導線を出さない）
- [ ] プライバシーポリシーが新仕様を記載（保存・所有者のみ・削除連鎖）

## 8. Task 分解（1つ＝1つの振る舞い）

1. [決定] 更新: CLAUDE.md ルール7 / AGENTS.md / 設計ドキュメント（承認直後・実装前）
2. インフラ: `rigel-photos` バケット作成 + wrangler.toml / env.ts / deploy ドキュメント
3. migration + PhotoRepository（D1。契約テスト）+ 退会カスケード追加
4. PhotoStore（R2 恒久。move = get→put→delete）
5. RunAnalysisJob: done 時の move + 行作成（失敗時は従来動作の回帰テスト）
6. routes: 一覧 + 配信（所有者ガード）
7. 削除連鎖: DeleteKifu / DeleteGame（+ 既存テストの拡張）
8. client: listGamePhotos ほか
9. web UI: 元写真ビュー
10. mobile UI: 元写真ビュー
11. プライバシーポリシー改稿
12. 本番 E2E: 解析 → 写真が残る → 閲覧 → 削除で消える

## 9. 検証 / eval 方針

- ゲート: typecheck / lint / format / test（全 Task で TDD）
- AI 精度: 影響なし（パイプライン不変）
- 本番検証: Task 12（審査ユーザーで一連の流れ）

## 10. リスク / 未決事項

- ストレージ増加が青天井（解析枠で月次は有界だが累積は無限）→ [未確定] の上限/圧縮で対応
- R2 の move はアトミックでない（get→put→delete）→ put 成功後に delete。途中失敗しても
  tmp 側は TTL 1日で消えるだけで二重課金等の実害なし
- 審査観点: 写真保存はプライバシーポリシー記載があれば問題ない想定（カメラ/フォトの
  利用目的文言は既存のまま）
