# Plan: 解析の非同期ジョブ化（202 + ポーリング）

> 状態: **提案（未承認・2026-08-01）**。ストア提出前のブロッカー。
> 背景: 実写真の Gemini 読み取りは1呼び出し 10〜150 秒（2026-08-01 AI Gateway 実測。
> 合成画像は即答するため開発中は顕在化しなかった）。河4方向は既に並列
> （gemini-analyzer.ts の Promise.all）だが、壁時計時間=最遅呼び出しで数分に達し、
> モバイル回線・OS のバックグラウンド遷移・fetch タイムアウトが接続を保てない。
> 同期 API（応答が返るまで接続を握る）という形が実写と両立しない。

## 1. 目的（なぜ）

撮影→解析（コアバリューの本線）を、実写真の遅い解析でも完走させる。
スマホを閉じても・回線が切れても、解析は進み、開き直せば結果に到達できる
（「何切るの回答を開き直しで復元」と同じ思想＝接続や画面の生存を前提にしない）。

## 2. ハーネス構成要素

**制約**（接続時間に依存しない実行形）＋**記憶・状態**（ジョブ状態の永続化）＋**観測**（ジョブの失敗理由）。

## 3. スコープ

- やること:
  - `POST /analyze` を **202 + jobId 即時応答**に変更。解析本体は同一リクエストの
    `ctx.waitUntil` で応答後も継続（**画像はメモリ内のみ＝画像非保存ルール堅持**）
  - D1 に `analysis_jobs`（id / userId / status: processing・done・failed / 結果 gameId・logId /
    失敗 reason / createdAt・updatedAt）。**画像・牌譜本体は持たない**（結果は従来どおり
    games/game_logs へ。ジョブ行は参照だけ）
  - `GET /analyze/jobs/:id`（本人のみ・RL_READ）。クライアントは2〜3秒間隔でポーリング
  - mobile: 送信後は jobId を永続化（アプリを閉じても再開時に復元してポーリング再開）。
    CaptureScreen の「解析中…」を「ジョブ進行中」表示に置き換え
  - web: 同じ非同期フローへ移行（クライアントは @rigel/client で共有）
  - 何切るの写真AI再現（/problems/analyze）も同じ仕組みに載せる
  - 滞留ジョブの扱い: 一定時間（例 10 分）更新が無い processing は failed 扱いで表示・
    再実行導線（waitUntil が途中で死ぬ可能性への備え）
- やらないこと（非対象）:
  - Cloudflare Queues / R2 への画像退避（**画像非保存ルールに抵触**。採るなら別途オーナー判断）
  - プッシュ通知での完了通知（将来。まずはポーリング＋復元）
  - Gemini 側の速度改善（モデル変更・thinkingBudget 調整は eval の領分 →
    [ai-model-selection 保留メモ]と接続。本 Plan は「遅くても完走する形」を作る）
  - 進捗率の表示（4方向の何個目か等。まずは processing/done/failed の3状態）

## 3-2. ポーリング予算（リクエスト数を暴れさせない）[決定 2026-08-01 オーナー懸念を受けて]

- **段階バックオフ**: 送信直後は 2 秒間隔、30 秒経過後は 5 秒、2 分経過後は 10 秒（上限）。
  5 分ジョブでも 1 ジョブあたり **50 リクエスト前後**に収まる（すべて軽い D1 の主キー読み）。
- **フォアグラウンドのみ**: ポーリングは画面が生きている間だけ（AppState が background に
  なったら止め、復帰時に再開）。バックグラウンドタイマーは持たない。
- **ハードストップ**: ジョブ送信から 10 分で必ず打ち切り（滞留扱い→再実行導線）。
  タイマーの消し忘れで無限に叩き続ける事故を構造的に防ぐ（1 ジョブの総ポーリング数に上限）。
- **サーバー側の整合**: RL_READ（IP 単位）の制限値がバックオフ最小間隔（2 秒=30req/分）を
  許容することを確認する（Task に含む）。
- 将来リクエストをさらに絞りたくなったら: 完了プッシュ通知 or long-poll（本 Plan 非対象）。

## 4. `[決定]` / `[未確定]` の仕分け

- 依拠する `[決定]`:
  - 画像を保存しない（CLAUDE.md ハードルール7）
  - 課金は成功時のみ・実呼び出し数ぶん加算（ハードルール6。waitUntil 内でも同じ経路）
  - 保存上限・plan 別枠の既存チェックは解析開始前に同期で行う（即時 4xx を返せる）
- 触れる `[未確定]`（本実装の前に検証タスクを置く）:
  - ~~`ctx.waitUntil` が応答後に数分の I/O 待ちを完走できるか~~ →
    **[決定 2026-08-01 本番実測] 不成立。** `/debug/wait-until-probe` で実測した結果、
    30秒のチェックポイントに到達する前に
    「waitUntil() tasks did not complete within the allowed time and have been cancelled」
    で打ち切られた（応答後の許容時間は実質 ~30 秒）。実行基盤は差し替えが必要:
    - ~~候補A: Durable Objects（メモリ内画像）~~ / ~~候補B: Gemini 高速化で30秒枠~~ →
      **[決定 2026-08-01 オーナー] 候補C（R2 一時保存 + Queues）を採用**。
      「画像の一時保存を許可・無理にメモリ完結にしない」の判断を受け、ハードルールを
      「恒久保存しない（解析ジョブ間の R2 一時保存のみ可）」に変更済み
      （CLAUDE.md ルール7・設計ドキュメント 2章/5章）。
    - 採用構成: POST /analyze → 同期検証 → 画像を R2（`jobs/{jobId}/...`）へ →
      ジョブ作成 → **Queue へ {jobId, 画像キー} を送信** → 202。
      Queue consumer（同一 Worker の queue ハンドラ・バッチ1件）が R2 から画像を取り、
      既存パイプライン（AnalyzeAndSaveKifu.execute）を実行 → done/failed →
      **一時画像を必ず削除**（成功・失敗とも。保険 = R2 のオブジェクトライフサイクル
      ルールで「作成から1日で削除」をバケットに設定）。
      Queues consumer は最長 15 分（公式に文書化された実行形）なので 150 秒級の呼び出しでも
      完走する。アカウントは Workers Paid（Queues 利用可能なことを確認済み 2026-08-01）。
  - 実機のポーリングとバックグラウンド復帰の挙動（iOS/Android でアプリ再開時に
    ポーリングが再開されるか）

> 注: ジョブの器（analysis_jobs / StartAnalysisJob / 202 ルート / ポーリング API）は
> 実行基盤がどれでも共通に使える。実装済み分は無駄にならない。

## 5. 影響範囲

- apps/api: ルート（analyze・jobs）、application（AnalyzeAndSaveKifu を「ジョブ開始＋
  waitUntil 継続」へ分割）、infrastructure（analysis_jobs リポジトリ・migration）
- packages/client: `analyze` の契約変更（202/jobId）＋ `getAnalysisJob`
- apps/mobile / apps/web: 解析導線の UI（進行中表示・復元・失敗と再実行）
- スキーマ（背骨）への影響: なし（Kifu は不変。ジョブは API 層の DTO）
- 依存追加: なし

## 6. 信頼まわり

- 画像非保存: waitUntil 方式の核。ジョブ行にも画像・画像由来データを入れない
- 課金: 解析成功時のみ recordGeminiCalls（現行ロジックを waitUntil 内でそのまま使う）。
  ジョブ失敗時は非加算（従来どおり）
- Zod 検証・null 白旗: 解析パイプライン自体は不変
- 認可: ジョブ参照は所有者のみ（userId 照合）。jobId は UUID（推測不可）

## 7. 受け入れ条件（= 最初に書く失敗テストの集合）

- [ ] `POST /analyze` は検証（認証・枠・上限）通過後、即 202 と jobId を返す
- [ ] 枠不足・上限超過は従来どおり同期の 4xx（ジョブを作らない）
- [ ] ジョブ完了で status=done・gameId/logId が取得でき、牌譜が保存されている
- [ ] 解析失敗で status=failed・reason が取得でき、課金カウントされない
- [ ] `GET /analyze/jobs/:id` は他人のジョブに 404
- [ ] mobile: 送信→アプリ再起動→jobId 復元→done で結果画面へ遷移できる
- [ ] 一定時間更新の無い processing はクライアントで失敗扱い＋再実行導線
- [ ] （検証）本番 waitUntil で 3分超の疑似処理が完走し D1 に書ける

## 8-2. UX 設計（[決定 2026-08-01 オーナー] 案B「送信したら一覧へ」）

- **フロー**: 撮影画面で送信（202）→ 即座に牌譜一覧へ遷移 → 一覧先頭に「解析中カード」→
  完了でカードが実カード（保存された半荘）に差し替わる。「待たなくていい」を UI で体現する。
- **ポーリングの一本化**: 画面ではなくグローバルな `AnalysisJobProvider`（App ルート）が
  pending ジョブの復元・ポーリング・状態を持つ。画面遷移・開き直しでも進行が生き、
  二重ポーリングが構造的に起きない。CaptureScreen からポーリング責務を撤去。
- **解析中カード**（牌譜一覧の先頭・通常カードと同じ意匠の枠）:
  - processing: スピナー＋「AI解析中…」＋「東一局を作成しています」（PendingAnalysis に
    seq を持たせて局名表示）＋「アプリを閉じてもOK・完了すると自動で追加されます」
  - failed / timeout: danger 色の枠＋理由の日本語＋✕（dismiss で消す・SecureStore も掃除）
  - done: カードを消して一覧を再取得（実カードが先頭に現れる）
- **撮影画面**: 送信の同期エラー（枠切れ 402 等）は従来どおりその場でインライン表示。
  202 が返ったら Provider にジョブを渡して一覧へ遷移（画面に残らない）。
- **web**: 当面は現行（モーダル内で待つ）を維持。一覧への解析中行は mobile の様子を見て判断。
